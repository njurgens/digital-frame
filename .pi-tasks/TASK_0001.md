GOAL
Implement an `AlbumProvider` abstraction layer that decouples the `SlideshowPlayer` from directly reading image files off the filesystem. Done looks like: a new `AlbumProvider` protocol (or abstract base class) is defined in `src/piframe/` with a method to retrieve a list of `Path` objects representing available photos; a concrete `DirectoryAlbumProvider` implementation is created that reads supported image files (`.jpg`, `.jpeg`, `.png`, `.gif`) from a configurable directory (matching the current `SlideshowPlayer.rescan()` behavior); `SlideshowPlayer` is refactored to accept an `AlbumProvider` dependency instead of reading `config.sync.output_dir` directly in `rescan()`; `PlayerModule` is updated to construct and inject the `AlbumProvider` into `SlideshowPlayer`; and all existing functionality (shuffle, interval, transitions, rescan on sync) is preserved without behavioral change.

CONSTRAINTS
- Preserve all existing file paths, function signatures (except the explicit delta in `SlideshowPlayer.__init__` and `PlayerModule.create`), and module names verbatim.
- Do not modify `SyncService`, `CacheModule`, `WifiModule`, `SettingsModule`, `ConfigStore`, `PhotoCache`, `BacklightController`, `ClockWidget`, `SleepScheduler`, `OverlayUI`, `Keyboard`, `Assets`, or any widget modules unless explicitly required for the album provider wiring.
- The `SlideshowPlayer.rescan()` method must continue to support shuffle (`config.slideshow.shuffle`) and Fisher-Yates shuffling exactly as implemented.
- The supported image extensions (`.jpg`, `.jpeg`, `.png`, `.gif`) must remain unchanged.
- The `EVT_SYNC_COMPLETE` event flow (`SyncService` → `App` → `player.rescan()`) must be preserved.
- Preserve all existing dependencies in `pyproject.toml` — do not add or remove any.
- Preserve the existing `DimModule` protocol pattern for DI modules.
- Do not change the `slideshow` entry point (`piframe.app:main`).
- Do not touch the `framesync` submodule or any system-level configuration (systemd, labwc, backlight sysfs).

KNOWN-UNKNOWNS
- Should `AlbumProvider` be a `Protocol` (structural typing) or an abstract base class (`ABC`)? The project already uses `Protocol` for `WifiManagerProtocol` in `types.py`.
- Should the `AlbumProvider` interface return `list[Path]` or a lazy iterator/generator? The current implementation materializes a sorted list before shuffling.
- Should `AlbumProvider` expose a `directory` property or method for the sync service to know where to write synced photos? Currently `SyncService` writes to `config.sync.output_dir` independently.
- Should the `AlbumProvider` be configurable via `config.toml` (e.g., multiple albums/sources) or is a single directory source sufficient for this issue?
- Should there be a `DefaultAlbumProvider` alias or factory in the modules package, or is `DirectoryAlbumProvider` the only implementation for now?

EXTERNAL-DEPENDENCIES
- None. This task is purely local refactoring within the `piframe` package. No third-party APIs, SDKs, services, or cloud products are introduced or modified.
